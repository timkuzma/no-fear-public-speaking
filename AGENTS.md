# No Fear Stage pilot

## Working boundaries

- Serve `public/` and the API through `server/app.py`, on the same origin. Root `index.html` and `styles.css` are imported legacy copies, not the maintained application.
- Keep native JavaScript/CSS. Starting practice requires an account. Keep legacy guest-draft import after authentication so existing recordings are not lost; do not expose a new anonymous practice route.
- API and module boundaries are in `docs/api-contract.md`. Private recordings are outside `public/`; every practice, job and media request must enforce ownership on the server.
- SQLite WAL, private media and durable queues form a single-host pilot. Run exactly one application process, with one final-job worker and one incremental-ASR worker; startup queue recovery is not safe across simultaneous application instances sharing a database.
- Do not simulate authentication, store passwords/session tokens in localStorage, or expose provider credentials in frontend source. Never commit `.env`, private data, logs or temporary test artifacts.
- Provider output is untrusted text. Verify transcript quotations; derive numerical metrics locally. Do not claim voice, gesture or psychological analysis from a text pipeline.
- `docs/ai-quality-implementation-plan.html` and `docs/research/` own the research rationale. Candidate contracts are implemented in `docs/ai-quality-contract.md` and `server/feedback_prompts.py`; prompt/schema changes require version updates and comparison against the immutable `evals/speech-feedback/baseline/` hashes. Never edit baseline snapshots. Quote-ID and mocked-provider tests prove structural provenance, not semantic entailment or live coaching quality.
- The candidate publisher withholds unreviewed freeform rewrite examples (`withhold_unreviewed_rewrites-v1`): validate the draft field, then publish null and exclude it from compatibility text/export. Preserve stored legacy reports. Raw drafts belong only in private eval artifacts; a withheld example is not a fact-preservation pass and does not certify the remaining advice.
- General feedback is independent of user-selected criteria. Trusted coaching guidance lives in `server/coaching_context.py`; primary-source adaptations are documented in `docs/research/coaching-question-feedback.md`. Inline quote membership checks contain literal source errors only, not semantic entailment. Do not criticize punctuation introduced by ASR. The tested default chat alias is `gpt-5.4`; catalog availability alone does not prove endpoint compatibility. Explicit older-version report refresh preserves media and old report JSON until success; the old successful job result remains the archive. Never regenerate history automatically.
- New reports allow empty findings and a nullable main focus derived only from a saved recommendation. Exact source offsets are Python Unicode code points, bound to transcript SHA-256. Keep speech, saved questions and confirmed answers separate; private question provenance is never public question data. Capture completeness cannot certify ASR lexical fidelity: current absence conclusions remain unknown.
- Evaluation uses synthetic development/calibration data; locked acceptance requires a measured baseline, two independent human reviewers and frozen gates. Real text-provider runs must use the existing durable ledger inside the application container, explicit per-run caps and one HTTP attempt per task; no ASR or extra production critic is implied. `scripts/evaluate_ai.py` never initializes or migrates the live ledger.

## Interface and Russian copy

- Product copy describes the user's task and result, never server/queue/provider/ASR/storage mechanics. Keep actionable save/device/recovery guidance in plain language. Translate application-owned legacy report labels only; never rewrite the user's speech, quotations or substantive findings. Validation errors name only fields that actually failed.

- `docs/prospect-faq.md` owns prospect FAQ copy and its research rationale. Landing FAQ answers connect a concrete preparation problem to an available practice action and its use before a real speech. Keep account/device/recovery details in their relevant flows; never substitute technical mechanics for the reason to practice or invent outcome guarantees.

- The public interface has no example report or report preview. Old `#/example` links redirect to the landing page; account reports still use real saved recordings.
- No logo or wordmark appears in the header. Guests have separate login/registration links; authenticated users have practice/history navigation and a separate logout action. All account-creation CTA labels are `Регистрация`.
- `public/typography.js` binds short Russian function words to the following word in rendered text across routes and live updates. Apply only to text nodes; never rewrite HTML, form values, stored transcripts or provider evidence. Keep editable/code regions excluded and preserve explicit newlines.
- Public privacy/consent pages and the registration consent control are currently removed; legacy `#/privacy` links return to the landing. Registration must not silently send consent. New accounts store the historical consent flag as false; it is no longer an upload gate. Ownership, authentication, origin and CSRF checks remain mandatory.
- Scenario explanations share a CSS grid cell to reserve the tallest copy's height. Keep their CTA outside the animated copy; switching contexts must not recreate or move the button.
- Practice-home continuations use `.practice-continuation`, section-size headings and spaced neutral rows; do not inherit the centered `.narrow` layout or history-page divider rules. Separate onboarding blocks and custom setup with whitespace rather than horizontal lines.
- Auth responses include provider/invitation flags; do not delay a successful registration with a redundant `/auth/me` request. Keep auth requests and IndexedDB operations bounded, and retain form values on failures. Test UI auth on a separate fixture origin (`--port 8095 --origin http://127.0.0.1:8095`) when a user is viewing localhost:8094.
- Landing styles and finite entrance animations live in `public/landing.css` and `public/landing-motion.js`. Content is visible by default; route replacement must clean up animations, observers and preference listeners. Honor reduced motion. Fonts are self-hosted with their OFL licenses in `public/fonts/`.

- Apply these rules across every route and shared component, including generated report titles.
- Use complete, connected headings and prose. Do not force line breaks or split one idea into a sequence of tiny sentences. Let text wrap naturally. Headings never end in a period; preserve question marks and meaningful source text outside headings.
- CTA labels contain no decorative arrows. Do not use decorative online-status dots or padded numbering such as `01`, `02`, `03`. Use ordinary numbering only for a meaningful sequence.
- Native single-select chevrons need an explicit inner right gutter and reserved text space. Keep keyboard interaction and native accessibility; do not replace selects with decorative divs.
- Typography uses shared CSS tokens: distinguish page titles, section headings, field labels, input values and hints by size, weight, spacing and contrast. Keep optional-field labels inline and attach hints to their field group.
- Main prose, questions and report content use `--text-body` (16px minimum); compact metadata uses `--text-small`. Keep the green accent for the main action and use neutral surfaces plus explicit checked/focus indicators for static content and choices. Short, narrow meeting viewports use the stacked chat layout for zoom reflow.
- Visuals must suit a contemporary Russian audience and recognizable local settings. Do not infer or claim real people's nationality from appearance. Record generated-asset provenance; never present an illustration as a real user or testimonial.
- Keep imagery bright, naturally colored and welcoming. Do not equate Russian context with gloomy or desaturated photography. Avoid copy overlays across faces; landing cards must convey a specific product benefit or a clearly labeled example.

- Recording is an immersive meeting scene, with one device toolbar and optional self-video. Keep speech advice and audience labels off this screen. Camera captures video plus audio; AI receives the audio track and transcript, not visual analysis. Speech and answers auto-save on recorder completion (manual or timer). One ready action starts the current meeting session; reuse mic/camera tracks across saving and question generation, reveal questions sequentially, and start each answer immediately when its question appears. Cancel automatic capture on navigation, logout, mute or lost device access; resumed sessions require a fresh ready action. Upload, retry and question generation stay in the same meeting DOM; never replace the audience/self-video for these transitions. Failed upload retains the Blob and offers retry. Guests save locally and see the authentication continuation in this meeting chat. Keep routine playback and downloads in the final report; only interrupted or conflicting drafts need explicit recovery. Questions map to confirmed saved answers.
- Logged-in speech also captures independent 5-second mono 16 kHz PCM WAV chunks through an AudioWorklet. Keep incremental transcription progress, recognized-word counts and fallback mechanics out of the meeting UI; recording status and actionable device/save errors remain visible. Never upload MediaRecorder timeslice blobs as standalone audio, transcribe the microphone check, or send guest audio before authentication. Keep full recording as the fallback; reuse live transcripts only for the bound capture session with complete indices, offsets, final manifest and matching duration. Provider question objects must select server-issued speech evidence IDs; public questions remain strings.

## Validation and operations

- Use Python 3.12+ in `.venv`; `pytest -q` covers API isolation, jobs and provider validation. Check both frontend modules with Node syntax checks, and verify the actual UI in a browser.
- The deterministic browser acceptance fixture is `tests/browser_flow_server.py`: loopback port 8094, temporary data, synthetic provider functions and test-only fault endpoints. Never include its fault routes in the maintained app or production container.
- Its `/__test__/meeting` entry installs `tests/synthetic-media.js` before the real application: generated audio/video exercise native browser codecs and worklets without physical device access. Track device-request counts through the fixture's body data attributes; keep this shim outside `public/`.
- `scripts/run-local.sh` starts the maintained app. Environment variables are not automatically read from `.env`; export them privately before starting.
- Production operations are in `scripts/production.py` and `docs/operations.md`: one Linux host, immutable image IDs, maintenance until readiness, automatic pre-activation recovery, and code-only manual rollback preserving current data. Keep schema-family labels honest; incompatible migrations require a new family and explicit recovery procedure.
- Runtime holds the instance lease and a shared data lease; offline backup takes the exclusive data lease. Stop the application before copying, verify checksums and rehearse restore into a new location. Never manipulate live SQLite across host/container kernels; use `docker exec` for the CLI.
- All production provider HTTP attempts require `limits.provider_scope` and a durable reservation before transmission. Retries and unknown outcomes count towards rolling work caps; these caps are not monetary billing. Persist operator pause and keep recordings on budget/queue failure.
- Shared-host TLS may terminate in HAProxy; use the loopback Nginx variant and exact hostname routing. Never replace another project with a similar title/domain. The Certbot hook must ignore other lineages and preserve the last valid PEM on failure.
- Operational status/alerts must be content-free. Local encrypted copies must not claim offsite protection. Timer/proxy templates require actual host installation; external monitoring runs on a separate host.
- Load tests of ordinary authenticated endpoints do not prove LLM generation capacity. Label real provider calls separately; unknown billing/token counts stay unknown.
- The 12 October 2026 gateway audit found no declared `spend` currency and zero Whisper expense despite nonzero audio seconds. Reconcile request logs with the asynchronously updated key counter; do not equate its audio meter with free upstream service or RUB settlement. Evidence and limitations are in `docs/observability-cost.md`.
- Guest and account recording drafts use the existing IndexedDB store on the browser origin, with a 24-hour restore window. Account drafts are scoped to owner/practice/stage; a bound guest import must not resume in a different account. Keep credentials out of this store. Preserve original Blobs and stable capture keys across login/reload; retire a draft only after matching server acknowledgement or explicit discard. Completed answers are queued in memory and written to IndexedDB alongside background uploads; proceed to the next question immediately without a countdown. Local optimistic segments are UI-only and must never authorize reports or claim server persistence. Upload acknowledgements update chat labels without rebuilding an active recorder; start the report only after all queued answers are acknowledged. Restore multiple drafts in ascending stage order and preserve bytes/client keys on retry. Interrupted aggregate MediaRecorder checkpoints require review and must never be treated as standalone timeslice audio. Import retries use an account-scoped `idempotency_key`; segment retries use `client_key` plus the original-byte hash. Legacy unconfirmed drafts and interrupted fragments need explicit continuation; newly completed answers auto-save. Keep failed jobs on explicit retry.
- Selected repeat focus is resolved on the server from an owned persisted report and kept separate from original user criteria. Never replace those criteria with model advice or accept client-supplied advice as provenance.
- Practice gives feedback on the user's actual speech; never impose a pre-recording content checklist or a project-defense template. The main setup exposes optional topic and speech duration as separate whole-minute and whole-second fields (30–600 seconds combined; serialize as fractional minutes for the existing API) for every user; questions are additional time, never a silent cut to seven minutes. Optional topic is weak context in both questions/report inputs, not a compulsory content criterion. Only explicitly selected user criteria become report criteria. Recommendations after recording must be grounded in the speech and its purpose/genre.
- First-user onboarding uses the same visible topic/time setup as later practices, followed by three audience questions in a meeting chat. Users can disable questions in additional options. Saving continues to the next question or a durable analysis job; a failed job start must retain the saved recording and offer continuation. Repeat practices use the selected recommendation, and choosing a repeat or another topic completes onboarding.
- README and UI are Russian; technical documentation is English. Update relevant documentation when changing API or operational behavior.
- Review changes and commit only relevant files. Use branch `frentend`; do not modify remote `main`. Report local, pushed and externally deployed status separately.
