Проверка: 11 октября 2026. Цель — работающий публичный инструмент, в котором человек записывает выступление, получает разбор своей речи, применяет рекомендацию и повторяет тренировку.

Сейчас готов фронтенд-прототип. Полноценного серверного продукта в переданном архиве нет. Главная недостающая часть — надёжный цикл «запись → распознавание → разбор → сохранённый результат». Подключение текстовой LLM само по себе этого не решает.

Это план работ, а не отчёт о выполненном production-релизе. Архитектура, сроки, квоты и пороги ниже — предлагаемые решения. Реальный backend, если он существует отдельно, ещё не исследован.

Рабочий кандидат для первого технического прототипа: Whisper → GigaChat → JSON-валидация. Это предварительный выбор по успешным тестам, а не окончательный выбор лучшей модели. owned_by: openai возвращается даже для GigaChat; не использовать это поле как доказательство фактического поставщика.

До пилота провести одинаковую оценку минимум двух подходящих текстовых моделей на 20–30 разрешённых записях. Набор должен включать разную длину, шум, паузы, слабую структуру и пользовательские критерии; отдельно добавить тишину и попытки заставить модель игнорировать инструкции. Сравнивать пригодность рекомендаций, точность цитат, задержку, долю ошибок и фактическую стоимость. Не отправлять записи реальных пользователей до определения условий их обработки.

Оценивать структуру, аргументы, примеры, соответствие теме/критериям и качество ответов по тексту. Темп рассчитывать по числу слов и измеренной длительности; паузы — по аудио, а не выдумывать LLM. Точность слов-паразитов требует отдельной проверки: ASR может удалять их. Не выводить мимику, зрительный контакт, уверенность или психологическое состояние из одной транскрипции.

В результате хранить: версию схемы и промпта, модель, вывод, 2–3 сильные стороны, 1–3 конкретные рекомендации, ссылки на фрагменты/цитаты, статусы доступности метрик. Недостаточно данных — отдельное состояние. Не подменять ошибку реального анализа демо-результатом.

Для формата данных опираться на Structured Outputs, но возможности конкретного шлюза проверять отдельно. Для загрузки аудио — на Transcription API; лимиты OpenAI не считать автоматически лимитами агрегатора.

04Целевой путь пользователя и onboarding

Основной цикл: задача → короткое выступление → конкретный разбор → один выбранный совет → повтор → проверка улучшения. Возвращение должно происходить ради прогресса, а не ради ещё одного отчёта.

  1. Главная объясняет результат: «Запиши выступление и получи 3 совета по своей речи». Показать пример отчёта до регистрации.
  2. Сохранить гостевой вход. Предлагаемая стартовая квота: одна короткая AI-проба до 60 секунд в серверной гостевой сессии; затем аккаунт. Квота контролируется сервером, не localStorage. Массовое создание гостей ограничить общей квотой и защитой от злоупотреблений; cookie/IP сами по себе не гарантируют уникальность человека.
  3. Onboarding задаёт цель: защита, выступление или свободная практика. Профиль пользователя необязателен. Объяснить: микрофон нужен, камера по выбору, что отправляется на обработку и как удалить запись. Для первой попытки рекомендовать 1–3 минуты вместо обязательного заполнения всех настроек.
  4. Проверка: отдельные действия для микрофона и камеры, короткая проба записи с прослушиванием, понятное исправление отказа. Камера не должна мешать аудиотренировке.
  5. Выступление: обратный отсчёт, таймер, завершение, отмена с подтверждением и лимит максимальной длительности. Предупреждение до достижения лимита. Не обещать, что вкладка может безопасно закрываться до подтверждённой загрузки.
  6. После речи остановить запись и загрузить её. Сервер создаёт транскрипцию. Для сценария с вопросами LLM формирует 3 вопроса по сказанному; экран показывает реальный этап ожидания. При ошибке предложить повтор загрузки/вопросов либо перейти к разбору одной речи.
  7. Ответы записывать отдельными сегментами. После каждого — подтверждённая загрузка; не включать ожидание модели в время выступления. Пользователь может пропустить вопрос или завершить раньше.
  8. Итоговый разбор: объединить транскрипции речи и ответов, валидировать результат, сохранить и открыть отчёт. Обновление вкладки во время обработки возвращает тот же статус.
  9. Отчёт связывает советы с цитатами/таймкодами. Предложить выбрать один совет и повторить. История аккаунта доступна после повторного входа; скачивание и удаление понятны.
  10. После первого результата короткий feedback: полезность, удалось ли понять следующий шаг, что помешало. Предложение зарегистрироваться объясняет пользу сохранения и повторов.

Особенно исправить текущие места: статичные вопросы; демонстрационные метрики; отсутствие логина; потерю медиа после обновления; отсутствие серверного восстановления; состояние ожидания без этапов и отмены; hardcoded demo-labels даже после будущей замены адаптера. getQuestions(config) нужно расширить серверным attemptId/транскрипцией. Большой Blob нельзя просто передать текстовой LLM как существующий объект JavaScript.

05Предлагаемая архитектура

Если отдельного backend нет: один backend, например FastAPI, PostgreSQL, закрытое S3-совместимое хранилище и worker из того же проекта. Статика и /api публикуются под одним HTTPS-доменом через reverse proxy. Сначала использовать PostgreSQL и для очереди задач; отдельный Redis и микросервисы добавлять только по измеренной необходимости. Если backend уже разрабатывается, сохранить его стек и согласовать этот контракт.

Схема компонентов

Зелёным отмечен существующий frontend. Остальные компоненты — предлагаемая серверная часть. Очередь находится в PostgreSQL; отдельный Redis для пилота не нужен.

Текстовая схема
Браузер: public/ · onboarding · запись · результат
                │ HTTPS / сессия / запросы статуса
        Домен + TLS + reverse proxy
          ├─ статический frontend
          └─ Backend API ───────────── PostgreSQL
                │                      users / sessions / attempts
                │                      jobs / results / events / usage
                ├─ закрытое object storage: аудио / опциональное видео
                │                              ▲
                └─ durable job ── Worker ───────┘
                                     │
                              извлечение аудио
                                     │
                          ASR → вопросы → LLM-разбор
                                     │
                               JSON-валидация
                                     │
                         результат + usage + события

API / worker → JSON-логи + сохранённые метрики → экспорт / обзор

Это целевая схема. В текущем архиве присутствует только браузерная часть.

Данные и API

Минимальные сущности: users, sessions, attempts, media_segments, jobs, analysis_results, product_events, llm_usage. В попытке хранить владельца (account или guest session), config, timestamps, статус, ссылку на результат и ошибку. Текст/медиа отделить от эксплуатационных логов.

Предлагаемый контракт: /auth/register, /auth/login, /auth/logout, /auth/me, подтверждение email и восстановление; POST /attempts, POST /attempts/{id}/segments, POST /attempts/{id}/questions, POST /attempts/{id}/analyze, GET /attempts/{id}, GET /attempts, DELETE /attempts/{id}. Для больших файлов можно выдать короткую подписанную загрузку, ограниченную конкретным сегментом. Сервер проверяет фактический файл, размер, формат и длительность; наличие загрузки подтверждается до создания AI-job.

API отвечает быстро: принял задание → 202 + attemptId/jobId; обработка выполняется в worker. Статусы: draft → uploaded → transcribing → questions_ready → answers_uploaded → analyzing → completed; отдельно failed/cancelled и путь без вопросов. При длительном ожидании пользователь видит этап и может вернуться в историю.

Job должен переживать перезапуск: lease/heartbeat, ограничение конкурентности, тайм-ауты, retries с backoff для временных ошибок, terminal error для неверного файла. Идемпотентность по attempt + segment + operation + version; повтор запроса возвращает существующее задание. Не обещать exactly-once вызовы внешней модели: при неопределённом ответе повтор может быть тарифицирован, это должно попадать в usage/резерв бюджета. Удаление попытки блокирует новые jobs и повторное появление результата от уже работающего worker.

Базовая политика пилота на согласование: до 10 минут речи и 3 ответов до 90 секунд; максимум 3 полноценные тренировки на аккаунт в день; 1 активная обработка на пользователя; audio-first, медиа до 30 дней, результаты до удаления аккаунта, технические логи 30 дней. Это продуктовые настройки, не требования конкурса и не юридические сроки. Выбранные сроки должны совпадать с интерфейсом, конфигурацией, удалением и политикой бэкапов. Снять нынешние 30 минут только после проверки длинных файлов и бюджета.

Авторизация и доступы

Использовать поддерживаемую библиотеку авторизации и server-side session в защищённой HttpOnly/Secure cookie, не хранить bearer-токены или пароль в localStorage. При email/password нужны хеширование пароля, восстановление через одноразовый токен, ограничение перебора, выход и отзыв сессии. Учесть CSRF, CSP и другие HTTP-заголовки в едином домене. Если уже есть подходящий auth-provider, интегрировать его вместо собственной реализации паролей.

Доступы: гость — только своя короткая попытка; пользователь — только свои записи/результаты; администратор — агрегированные метрики и ошибки. Доступ администратора к записи пользователя по умолчанию не нужен. «Школьник / студент / работаю» — профиль, а не роль безопасности. Проверять владельца во всех API, загрузках, скачиваниях, экспортах и удалении; знание UUID не даёт доступа. Проверить тестами два разных аккаунта и гостя. Связать гостевую попытку с аккаунтом после входа без копирования чужих данных.

06Метрики, логи и экономика

Минимально достаточно хранить product_events и llm_usage в PostgreSQL, серверные JSON-логи в устойчивом хранилище с ротацией и retention, предоставить защищённый CSV/JSON-экспорт и простой административный обзор. Не строить отдельную аналитическую платформу до пилота. Мониторинг CPU/RAM/disk, API p95/error rate и очереди обязателен; позднее эти данные можно подключить к внешней системе.

События: onboarding_started/completed, devices_check_succeeded/failed, recording_started/completed, upload_succeeded/failed, questions_ready, analysis_succeeded/failed, result_viewed, recommendation_selected, repeat_started, feedback_submitted. Исключить секреты, пароли, email, полные транскрипции и аудио из event payload и логов.

Как считать cost/DAU

Для одной тренировки с вопросами: 5 минут речи + суммарно 2 минуты ответов; 1 запрос генерации вопросов + 1 итоговый разбор; в сумме 6000 входных и 1800 выходных текстовых токенов. Это плановые допущения, их заменить медианой/p95 из usage пилота. Генерации изображений в Core Product Loop нет.

C_attempt = audio_minutes × P_ASR + input_tokens / 1 000 000 × P_in + output_tokens / 1 000 000 × P_out

C_AI_per_DAU = attempts_per_active_user_per_day × C_attempt × reserve_for_retries

Иллюстративный ориентир: $0,006/минута для OpenAI Whisper-1 и $0,15/$0,60 за 1 млн входных/выходных токенов для GPT-4o-mini. Это публичные цены других прямых сервисов/моделей; они не являются тарифами whisper-large-v3 + GigaChat у предоставленного агрегатора. Актуальный ориентир проверен по Whisper и GPT-4o-mini.

При этих условных ставках: $0,042 ASR + $0,0009 input + $0,00108 output = $0,04398 за тренировку. С плановым резервом 20%: около $0,0528. Резерв не гарантирует покрытие всех повторов.

07Нагрузка и приёмка по 6 критериям конкурса

Главное уточнение: 10 HTTP RPS на backend и 10 завершённых AI-тренировок в секунду — разные нагрузки. Быстрый 202 не доказывает, что worker успевает обрабатывать очередь. Нужно показать пропускную способность, задержки и рост очереди.

Предлагаемая программа нагрузочных испытаний: k6 или эквивалент, внешний генератор вне сервера приложения, сохранённые сценарии и сырые результаты, фиксированная версия кода/конфигурации. Без токенов и пользовательских записей в отчёте.

Для массового API/stress-теста допустим управляемый stub провайдера, но он должен быть явно обозначен. Отдельный ограниченный тест реального провайдера обязателен; результаты заглушки не доказывают LLM-пропускную способность. Реальный прогон требует известного бюджета и квот; неизвестный timeout может означать уже тарифицированный запрос.

RPS — число HTTP-запросов в секунду. RPM — запросы к провайдеру в минуту. TPM — входные и выходные токены в минуту, также раздельно, согласно правилам конкретного провайдера. TPS в отчёте явно определить как выходные токены/секунду генерации; для streaming измерять first-token и last-token. При non-streaming доступен лишь completion_tokens / полное время ответа — это отдельная оценка, не чистая скорость декодирования. ASR отдельно: аудиоминуты/минуту и real-time factor.

Проверка размерности: 10 новых AI-попыток/с при 2 LLM-вызовах и 7800 суммарных токенах означают около 1200 LLM RPM, 4,68 млн TPM, 18 тыс. выходных токенов/с и 4200 аудиоминут/минуту. Это расчёт требуемой нагрузки, не достигнутый результат. Поэтому утверждение «выдерживаем 10 RPS» обязано сопровождаться профилем трафика.

Предлагаемые инженерные пороги до согласования: без потери принятой записи/задания; <1% неожиданных 5xx/timeout на API при 10 RPS; p95 CRUD/status ≤500 мс без учёта upload и AI; отсутствие бесконечного роста очереди на выбранном job arrival rate; восстановление очереди после spike; конечные failed-статусы и понятные сообщения. Для AI отдельно целевой p95: вопросы ≤30 с после принятия речи, полный отчёт ≤120 с после принятия последнего файла для согласованной длительности. Эти цели нужно проверить, не обещать по одиночным smoke-тестам.

08Алгоритм работ, зависимости и владельцы

Плановая оценка при отсутствии backend: 18–29 рабочих дней разработки и проверки, затем 7–10 календарных дней наблюдаемого пилота. Это оценка объёма для одного опытного разработчика с участием владельца продукта и проверяющего; не обещание даты. Готовый backend, доступ к hosting и своевременные решения могут сократить срок. Если работают несколько людей, часть UX и инфраструктуры можно готовить одновременно, но этапы приёмки сохраняются.

09Ворота готовности и запуск пользователей

Технические ворота перед приглашением:

  • Полный flow работает на внешнем HTTPS-домене; frontend не содержит LLM-ключа.
  • Реальная запись даёт реальную транскрипцию и конкретный разбор; тишина/короткая речь не дают выдуманную оценку.
  • Проверены Chrome desktop, Safari desktop, Safari iOS и Chrome Android на реальных устройствах: микрофон/камера, аудио без камеры, блокировка, прерывание, MP4/WebM, фон, плохая сеть.
  • Refresh после подтверждённой загрузки и restart worker сохраняют попытку; повтор запроса не создаёт ещё одну попытку; нет необработанных зависших jobs.
  • Проверены вход/выход/restore, чужие id, гостевая сессия, скачивание и удаление; quotas/rate limits нельзя обойти простым запросом API.
  • Сохранение и удаление медиа соответствуют показанным пользователю правилам; для пилота определены возраст/участники и согласия. Если приглашать школьников, отдельно решить условия участия до их приглашения.
  • Есть ежедневный просмотр failures/queue/usage/cost, экспорт метрик, бюджетный лимит, работающее резервирование и проверенный restore/rollback.
  • Нагрузочный сценарий 10 HTTP RPS пройден с объявленным профилем; граница реального LLM-throughput задокументирована отдельно.
  • Экспертная проверка 20–30 тестовых речей: предлагаемый порог ≥80% отчётов без существенных фактических ошибок и с полезным следующим действием; все показанные цитаты совпадают с транскриптом. Более высокий порог нужен для рискованных утверждений; в MVP такие утверждения исключены.

Пилот: начать с пяти наблюдаемых взрослых пользователей из одного сегмента, исправить основные препятствия, затем пригласить 20–30. Это предложение для уменьшения неоднородности результатов; сегмент выбирает владелец продукта. Не менять промпты незаметно: учитывать версию при сравнении качества.

Предлагаемые продуктовые ориентиры пилота: ≥80% начавших запись получают первый реальный результат; ≥70% оценивших отмечают полезность; ≥30% активированных начинают вторую тренировку за семь дней. Всегда показывать числитель/знаменатель, сроки и число ответивших. На малой выборке это ориентиры для решений, не доказательство product-market fit. D7 посчитать только для пользователей, у которых прошли полные семь дней.

Если технические ворота выполнены, но повторов мало — исследовать пользу советов и мотивацию; если первый результат недоступен — исправлять запись/загрузку/ожидание прежде привлечения новых пользователей. Если стоимость выше бюджета — ограничить длительность и concurrency, улучшить промпт/модель по eval, не ухудшая качество незаметно.

10Что нужно определить сейчас

  1. Есть ли отдельный backend и кто отвечает за его интеграцию; где код и API.
  2. Дата конкурса и обязательные требования к LLM/hosting; полный регламент.
  3. Первый сегмент и критерий успеха: например, студенты перед защитой, либо сотрудники перед рабочей презентацией.
  4. Hosting, домен, почтовый сервис, владелец аккаунтов и лимит расходов пилота.
  5. Реальные тарифы/квоты/срок действия агрегатора, допустимость обработки голосовых записей и условия хранения.

При отсутствии ответов этот план предполагает новый простой backend, приглашённый пилот для взрослых, audio-first и ограниченные тренировки. Эти допущения позволяют начать проектирование без расширения MVP.
